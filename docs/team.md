## 4. Git

- `main` は常に動く状態。feature ブランチ → PR → 相手がレビュー（5分）→ merge
- 1機能 = API + UI を縦に切って1PR
- コミット：`type(scope): 内容`。type は feat / fix / docs / chore / refactor
- コミット・PRに秘密情報、他社AIツール名、AI署名行を含めない
- 提出：11/10 午前に `git push submit main`（履歴ごと提出用リポジトリへ）

## 5. コード

- フォーマット・lint は ruff / prettier / tsc / pre-commit / CI に従う。手で整えない
- 外部I/O（Gemini, Firestore, Storage）は `services/` に隔離し、ルーターは薄く
- Gemini の出力は Pydantic でパース。失敗時は理由付きで 502
- 環境変数は `config.py` / `env.ts` に集約
- 例外を握りつぶさない。ログは構造化
- テストは schemas のパースと抽選ロジックの2本のみ（壊れると全部壊れる箇所に限定）

## 6. Own the Why — AIとの付き合い方

- 選択がある作業（ライブラリ・モデル・設計・プロンプト構造）は、AIに候補を2〜3個 pros/cons 付きで出させ、**人が選ぶ**。「決めて」と頼まない
- 理解して1分で相手に説明できないコードは merge しない
- AIが述べた API仕様・モデル名・料金・リージョン対応は、公式ドキュメントで確認してから採用する
- 任せる：ボイラープレート、設定、型生成、エラー原因の列挙、下書き
- 任せない：課題設定、何を作らないかの判断、技術選定の最終判断、語りの設計ルール、decisions.md の理由欄

## 7. 記録（その場で書く。後でまとめない）

- `docs/decisions.md`：選択したら5行（候補 / 選択 / 理由 / 捨てた理由 / 見直し条件）。目安 1日3〜5件
- `docs/ai-usage.md`：AIを使った場面を1行（場面 / 頼んだこと / 候補 / 採用 / 不採用理由）
- `docs/assets.md`：素材・ライブラリ・データの出典とライセンス（著作物利用シートの元）

## 8. やらないこと

- 他社LLM・他社AIサービスの利用
- 認証、課金、ネイティブアプリ、多言語
- 図鑑・復習・ストリーク等の定着装置（プロダクト哲学に反する）
- 11/9 夜以降の機能追加
